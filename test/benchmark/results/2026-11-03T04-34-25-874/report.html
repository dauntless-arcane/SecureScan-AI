Method and caveats

  1. Each repo is scanned through the public backend API (submit → poll → report), exactly as the UI does. The harness keeps its own checkout of the same commit to resolve ground-truth line anchors and to measure fix diffs.
  2. A finding is a true positive when it is in the same file, within 2 lines of a known vulnerability, and its CWE-derived category matches (or is closely related to) the vulnerability's category. Same place with an unrelated category is a "loose" match: counted separately, never as a TP.
  3. False positives come from two sources: findings on code labeled deliberately safe (all repos), and any unmatched in-scope finding for repos whose ground truth is marked complete. For other repos unmatched findings are "unlabeled": review them and promote real issues into ground truth, then re-score with `report.js --rematch`.
  4. OWASP Benchmark uses its own scoring rules: exact category match per test-case file; findings of other categories are ignored.
  5. "SAST-detectable" marks vulnerabilities a static scanner can reasonably be expected to see (injection sinks, weak crypto, secrets). Logic flaws such as IDOR, CSRF, or missing rate limits are listed for completeness but excluded from that recall figure.
  6. Fix verification only checks that the same Semgrep rule no longer fires on that file. It does not prove the fix is correct, compiles, or preserves behavior. Red flags (large rewrite, shrunk file, truncated context) mark fixes that likely silenced the scanner by deleting code or were produced from a truncated file.
  7. Upstream repos move. Ground-truth entries carry an anchor string and are relocated automatically when line numbers drift; entries whose anchor disappears are reported as stale and excluded from scoring.
